## Стек

**Frontend:** Next.js 16 (App Router, Turbopack), React 19, TypeScript strict, TanStack Query, Redux Toolkit, React Hook Form, Tailwind CSS 4 (CSS-first), SCSS-модули, axios, jose, react-hotkeys-hook, PWA (собственный service worker)

**Backend:** NestJS 11 (модульный монолит), PostgreSQL 17 + Prisma 7 (driver adapter `@prisma/adapter-pg`), JWT (access/refresh), Argon2, fluent-ffmpeg, @react-email + Nodemailer (Mailgun), helmet, class-validator + class-transformer

**Инфраструктура:** Turborepo + bun workspaces, Docker Compose (db + backend + frontend), Next.js standalone-сборка, деплой через Dokploy

## Задача

Пет-проект под портфолио: хотелось взять домен, где фронтенд не сводится к формам и таблицам, а бэкенд — к CRUD. Видеохостинг даёт обе сложности сразу: на сервере — приём тяжёлых файлов и транскодинг в несколько разрешений, на клиенте — плеер с переключением качества, горячими клавишами и корректной работой на медленной сети. Ограничения — один VPS без облачных сервисов и отсутствие бюджета на инфраструктуру, поэтому хранилище и обработка видео решены своими силами: файлы лежат в Docker-томе и раздаются через ServeStatic, а не в S3 с CDN. Это осознанный трейд-офф для проекта такого масштаба; путь миграции на объектное хранилище описан ниже.

## Технические решения

- **Транскодинг в несколько разрешений с прогрессом в реальном времени.** При загрузке backend через `ffprobe` определяет исходное разрешение и выбирает только те профили из набора 360p–4K, которые не превышают оригинал — апскейл не делается. Каждое разрешение кодируется последовательно через fluent-ffmpeg и складывается в отдельную поддиректорию (`uploads/videos/<quality>/<file>`), чтобы плеер мог переключать качество простой подменой URL, без манифестов и отдельного стриминг-сервера. Ответ на загрузку отдаётся сразу после сохранения оригинала, транскодинг идёт в фоне: клиент получает имя файла и опрашивает `GET /upload-file/status/:fileName`. Прогресс считается сквозным по всем разрешениям — доля текущего профиля складывается с уже завершёнными, поэтому шкала растёт монотонно, а не сбрасывается на каждом проходе.

- **Поллинг статуса обработки, который сам себя останавливает.** На клиенте статус транскодинга — обычный `useQuery` с динамическим `refetchInterval`: функция читает последнее значение прогресса и возвращает `3500` мс, пока он меньше 100, и `false` при завершении. Опрос прекращается без `useEffect`-таймеров и ручной очистки, а форма публикации разблокируется реактивно по достижении 100%. Тост об успехе подгружается динамическим `import()`, чтобы `react-hot-toast` не попадал в основной бандл страницы загрузки.

- **Плеер собран из независимых хуков вместо одного компонента-монолита.** Каждая ответственность вынесена отдельно: `usePlayPause`, `useVideoProgress`, `useVideoVolume`, `useVideoQuality`, `useFullScreen`, `useSkipTime`, `useVideoHotkeys` — все принимают общий `ref` на `<video>` и композируются в `useVideoPlayer`. Такая нарезка позволяет тестировать и менять поведение по частям. При переключении качества позиция воспроизведения сохраняется: хук запоминает `currentTime`, подменяет `src` на другой профиль и восстанавливает время, продолжая проигрывание — визуально это выглядит как смена битрейта, а не перезапуск ролика.

- **Горячие клавиши, не мешающие вводу текста.** Пробел обрабатывается собственным `keydown`-слушателем с проверкой `target`: если фокус в `input`, `textarea` или `contenteditable`, событие пропускается — иначе пробел ставил бы видео на паузу при наборе комментария. Остальные сочетания (`←/→` перемотка, `↑/↓` громкость, `m`, `f`, `t` — театральный режим) объявлены через `react-hotkeys-hook` с `preventDefault` на стрелках, чтобы страница не скроллилась.

- **Auth: httpOnly-cookie для refresh, проверка доступа на edge до рендера.** Refresh-токен живёт только в `httpOnly`-cookie и никогда не доступен JS; access-токен короткоживущий, пароли — Argon2, регистрация и вход закрыты reCAPTCHA, почта подтверждается письмом на @react-email. Приватные разделы (`/studio`, `/my`) защищены на уровне Next.js middleware: токен верифицируется через `jose` прямо на edge и неавторизованный пользователь редиректится на логин до того, как отрендерится страница — серверные проверки при этом остаются на API и остаются источником истины. Ресурсы студии проверяются на владение: видео редактируется и удаляется только каналом-владельцем, чужой `id` возвращает 403.

- **Разделение серверного и клиентского стейта.** Все данные с API (лента, видео, каналы, плейлисты, комментарии, история) живут в TanStack Query с инвалидацией по ключам после мутаций. Redux Toolkit оставлен исключительно под сессию — пользователь, `isLoggedIn`, access-токен — то есть под то, что не является кэшем ответа сервера. Серверные сущности не дублируются в стор, единственный источник истины — кэш Query.

- **PWA с раздельными кешами и осознанными исключениями.** Собственный service worker (без workbox) разводит трафик по трём версионированным кешам — статика, изображения, runtime — и обслуживает их по стратегии stale-while-revalidate; при смене версии старые кеши удаляются в `activate`. Навигационные запросы при офлайне падают на кешированную страницу или `/offline`. Принципиально исключены из кеша `/api/` и `/uploads/`: ответы API должны быть свежими, а видеофайлы при кешировании быстро переполнили бы квоту хранилища и ломали бы range-запросы плеера.

## Функциональность

- Загрузка видео с автоматическим транскодингом в доступные разрешения и индикацией прогресса обработки
- Плеер: переключение качества с сохранением позиции, перемотка, громкость, полноэкранный и театральный режимы, горячие клавиши
- Студия автора: список своих видео с поиском и пагинацией, создание, редактирование, удаление, обложки и теги
- Каналы: страница канала, подписки, баннер и аватар, счётчик подписчиков
- Лента и навигация: главная, тренды, категории, рекомендации с исключением уже просмотренного, полнотекстовый поиск
- Плейлисты, лайки, история просмотров и раздел «Понравившиеся» в личном кабинете
- Комментарии с проверкой владельца на редактирование и удаление
- Аутентификация: регистрация и вход с reCAPTCHA, подтверждение почты, настройки профиля
- PWA: установка на устройство, офлайн-страница, кеширование статики

## Архитектура

Монорепо на Turborepo + bun workspaces: два приложения с общим тулингом и единым `.env` для прод-стека.

```
apps/
  backend/               # NestJS (модульный монолит)
    src/
      auth/              # JWT-стратегия, guards, refresh-токены
      media/             # загрузка, транскодинг ffmpeg, пайпы валидации
      video/             # публичные видео, studio/ (CRUD автора), comment/
      channel/ user/ playlist/ category/ watch-history/ settings/
      email/             # @react-email шаблоны
    prisma/schema/       # схема, разбитая по доменам
  frontend/              # Next.js App Router
    src/
      app/               # (public) / auth / my / studio / offline
      components/ui/     # video-player (композиция хуков), video-card, ...
      services/          # слой доступа к API
      server-actions/    # middlewares защиты роутов (edge)
      store/             # Redux Toolkit: только сессия
    public/sw.js         # service worker
docker-compose.yml       # прод: db + backend + frontend
docker-compose.dev.yml   # dev: только PostgreSQL
```

На бэкенде бизнес-логика живёт в сервисах, Prisma используется напрямую без слоя репозиториев. Валидация входящих данных — DTO с class-validator, загружаемые файлы проходят через пайпы проверки типа и папки назначения.

### Известные ограничения

Транскодинг выполняется в процессе Node.js, а прогресс хранится в памяти (`Map`). Для одного инстанса это работает, но состояние не переживает рестарт и не масштабируется горизонтально. Следующий шаг — вынести обработку в очередь (BullMQ + Redis) с отдельным воркером и хранением статуса в БД; тогда же логично перевести хранилище на S3-совместимое с раздачей через CDN.

## Запуск

Требуется [Bun](https://bun.sh) ≥ 1.2.8, Docker и установленный ffmpeg.

```bash
git clone <repo-url>
cd adamix
bun install

# 1. Поднять PostgreSQL
bun run db:dev

# 2. Создать .env из примеров и заполнить значения
cp apps/backend/.env.example apps/backend/.env
cp apps/frontend/.env.example apps/frontend/.env

# 3. Применить схему к БД и засидить демо-данными
cd apps/backend && bun run db:reset && bun run seed:run && cd ../..

# 4. Запустить backend (4200) и frontend (3000)
bun run dev
```

Прод-стек целиком поднимается из корня:

```bash
cp .env.example .env     # заполнить значения
docker compose up -d --build
```

Обязательные переменные: `DATABASE_URL`, `JWT_SECRET`, `CLIENT_URL`, `API_URL`, `RECAPTCHA_SECRET_KEY`, SMTP-доступы, `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_RECAPTCHA_SITE_KEY` — полный список в `.env.example`.
